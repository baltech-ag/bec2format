# pack-bf3 rejects BF2 control tags

## Context

FW-898 switched the Bros2FW build to produce BF3 files directly through the
`bec2format pack-bf3` CLI. A regression from that switch reached a device: the
SM4200 and SM4500 peripheral firmware components were missing from the generated
`.bf3`, so LEGIC readers received no firmware update for those controllers. The
build reported success and printed no warning at all — 29 payloads were written
by the builder, 27 components ended up in the file.

Cause: those components reach the packer with BF2 tagtype `0x34`. Two places in
`bec2format` consult the same table, `BF2_TAGTYPE_MAP` in `bf3file.py`, which
deliberately maps the control tags `0x34` (SM4200 prepare) and `0x48` (SM6300
activate) to "no BF3 component":

- `Bf3File.bf2_import()` — the reader for legacy `.bf2` files. Skipping control
  tags here is **correct**: released `.bf2` files legitimately contain them.
- the `pack-bf3` CLI in `cli.py` — mirrored that skip, and silently returned
  `None` for such a component, which the caller then dropped without a message.

The second one is the bug. In the pack-bf3 path a control-tag component must
never be submitted in the first place: the manifest is generated by the caller,
and a caller emitting a control tag has made a mistake. Dropping it silently
turns that mistake into a firmware that is quietly incomplete.

## Changes

### 1. `bec2format/cli.py` — fail instead of skipping

The description builder loses its "no BF3 counterpart" escape hatch and instead
reports the condition through the same `_fail()` / `Bf3PackError` mechanism the
neighbouring manifest validations already use:

    <component>: tagtype 0x34 is a BF2 control tag and maps to no BF3 component

Consequently the "a component may be None" plumbing disappears from the
component builder and the packing loop — every entry in the manifest now yields
exactly one BF3 component or aborts the run. No output file is written and the
exit code is 1, consistent with every other manifest error.

### 2. `BF2_TAGTYPE_MAP` — unchanged, on purpose

The `0x34` / `0x48` entries stay exactly as they are. `Bf3File.bf2_import()`
keeps its own skip and therefore its silent behaviour; only the CLI becomes
strict. Verified before the change that the two paths really do have independent
skip logic, so tightening one cannot affect the other.

## Tests

- `tests/test_cli.py`: the existing test that pinned the silent drop is inverted
  — a manifest containing tagtype `0x34` must now exit 1, name the component and
  the tagtype on stderr, and leave no output file behind.
- `tests/test_bf2_import.py` (new): pins the other half of the contract. Builds a
  minimal in-memory `.bf2` stream and checks that a leading control tag is still
  skipped without complaint, producing the same single main-firmware component as
  the same file without it.

## Consequences for callers

Bros2FW must stop passing the control-tag components to the packer at all —
until it does, an SM4200/SM4500-bearing build fails loudly instead of silently
under-delivering. That is the intended trade, but it means the version pin bump
and the builder change have to land together.

Because the accepted-input contract of the CLI changes (manifests that packed
before are now rejected), this is released as a minor bump, 1.04.00, not a patch.
